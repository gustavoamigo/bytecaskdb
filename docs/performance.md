# ByteCaskDB Performance

Results of the benchmark run of 2026-10-07 at commit `e62d83f`: ByteCaskDB against [RocksDB](https://rocksdb.org/) at 1M keys, with 50k and 500k keys for the effect of dataset size. The full report of this run, with the dataset-size sweep and the optimistic-concurrency (CAS) benchmark, is [`bytecask_benchmark_showcase.md`](bytecask_benchmark_showcase.md), generated by `scripts/benchmark_showcase.py`.

- Keys are UUIDv7-like with five prefixes (`user::`, `order::`, …); values are 245 bytes of random, incompressible data. Recovery benchmarks write 1-byte values.
- Per-value CRC verification is disabled for read benchmarks; hint file CRC is always verified during recovery.
- ByteCaskDB runs on the default blind-leaf key directory and the buffer-pool read path. Each result is the mean of 5 runs.

## Summary

- **Point reads** reach 4.72 Mops/s at 1M keys, with p50 172 ns and p99 378 ns. Latency moves little from 50k to 1M keys (p50 154 → 172 ns).
- **Concurrent reads** scale with the cores: 31.5 Mops/s at 8 threads and 62.9 Mops/s at 32 on a machine with 8 cores and 16 threads. Reads are lock-free snapshots with no shared mutex.
- **Sequential writes** reach 99.0 Kops/s (NoSync) and 161.8 ops/s (Sync), limited by `fdatasync` round-trip latency. NoSync is slower than RocksDB at every measured size, and falls as the dataset grows (below).
- **Concurrent sync writes scale via group commit** — writers share a single `fdatasync` call. 8.4 Kops/s at 64 threads.
- **Range scans** of 50 keys, values included, reach 441.4 K scans/s. Every value is read individually from its record, where LSM engines pack values contiguously in sorted runs. This dataset fits in memory; scans over data larger than RAM were not measured. Key-only iteration (`keys_from`) reads each key's record header and skips the value.
- **Recovery is parallel**: 10M keys in 0.47 s from a cold start at 8 threads.

## Recovery

Recovery runs when ByteCaskDB opens an existing database: it rebuilds the in-memory key directory by reading compact hint files from disk. Each hint file holds its entries in zstd frames and is verified by a file-level CRC-32C trailer before parsing. This is parallelised across all available CPU cores — each core processes a disjoint set of hint files independently, and the results are merged before the database becomes available.

Measured from a cold start: every file of the database is evicted from the page cache before each open, so the hint files come off the SSD, as after a reboot or on a new node.

| Keys | Threads | Recovery Time | Speedup vs 1T |
|---:|---:|---:|---:|
| 1M | 1 | 262 ms | — |
| 1M | 2 | 148 ms | 1.8× |
| 1M | 4 | 97 ms | 2.7× |
| 1M | 8 | 67 ms | 3.9× |
| 1M | 16 | 58 ms | 4.5× |
| 10M | 1 | 2.57 s | — |
| 10M | 2 | 1.41 s | 1.8× |
| 10M | 4 | 0.82 s | 3.2× |
| 10M | 8 | 0.47 s | 5.5× |
| 10M | 16 | 0.62 s | 4.2× |

At 10M keys, 16 threads were slower than 8 in this run; the cause was not investigated. At 50k keys, recovery takes 35–38 ms at every thread count.

The benchmark's keys — prefixed UUID text written in order, with 1-byte values — compress 14×: at 10M keys the hint files hold 675 MB of entries in 47 MB (measured separately, in September 2026). Keys with less in common compress less (2.4× for random 16-hex-digit ids with realistic values, 1.6× for random binary keys), and a cold start then reads more; [`docs/hint_compression_design.md`](hint_compression_design.md) has the measurements.
