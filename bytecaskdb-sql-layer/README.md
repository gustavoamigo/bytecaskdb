# ByteCaskDB SQL layer

A PostgreSQL-dialect SQL layer over the ByteCaskDB engine. SQL is parsed, bound, planned, and compiled to native code in process, and the compiled plan runs against the engine through a small plan API. It is built for TPROC-C first, so its dialect is a growing subset of PostgreSQL 17, not all of it.

MIT, like the engine. It uses the engine's public API only (`include/bytecask.hpp`).

## How it works

```
SQL ─▶ libpg_query ─▶ AST ─▶ binder ─▶ logical plan ─▶ rewrites ─▶ search ─▶ physical plan ─▶ codegen ─▶ C ─▶ TinyCC ─▶ plan API ─▶ engine
```

- **Plans are C.** The compiler writes each statement as a C program against `algebra/bc_plan.h` and loads it with TinyCC. Only plans the layer generates run.
- **PostgreSQL decides semantics.** Results, errors (SQLSTATE) and NULL placement follow PostgreSQL 17; a model-based test compares the two statement by statement.
- **Never waits.** Nothing blocks on a lock. Snapshot isolation by default; a write-write conflict is retried (autocommit) or fails with 40001 (transaction). SERIALIZABLE, in the embedded API and over the wire, checks at commit that what a transaction read is unchanged.
- **Refuses rather than guesses.** A statement outside the dialect is refused with a message and its position (42601); one the planner can't plan, or a guard it can't give, is refused with 0A000.

## Conformance

How much of each suite the layer passes, from the functional suite's conformance run (`tests/functional/report.py`; every PR's CI run uploads the full report, with a table per SQL feature):

| Suite | Coverage | Tests | Checks |
|---|---|---|---|
| SQL:2016 Core (sqltest) | 84% | 623/743 tests | statement accepted |
| PostgreSQL features | 93% | 474/507 cases | results |
| ByteCaskDB features | 100% | 13/13 cases | results |
| TPROC-C | 100% | 1/1 case: five transactions, then consistency conditions 1–9 | consistency conditions 1–9 |

PostgreSQL 17 itself refuses 120 of sqltest's tests (non-PostgreSQL syntax such as `CHARACTERS` length units), so 623/743 is the most a PostgreSQL dialect can pass; the layer passes all 623.

The suite is young: its cases are the first of the plan in `docs/functional_testing_design.md`, so a high percentage means few cases, not wide coverage.

- **Plans after a DDL:** every cached plan binds again once after any DDL. By text (a simple Query, `execute(sql)`) a statement returns its catalog's columns; a prepared statement keeps the parameter types it fixed, and one whose result columns change is 0A000, as in PostgreSQL 17. - **Interfaces:** the embedded C++ API (`api/database.cppm`), with a row window on reads in a transaction (`Transaction::execute_window`: skip, limit, stop) and a cursor (`Transaction::open_cursor`, `Cursor::fetch` in any direction: it sees the transaction as of the call, and with `Holdability::Hold` outlives its commit on a snapshot of its own), and over the wire `DECLARE`, `FETCH`, `MOVE` and `CLOSE` of cursors, and `sql_layer_server`, a PostgreSQL wire-protocol server that psql, psycopg and HammerDB connect to. Trust authentication only: it listens on loopback unless told otherwise. It takes `CancelRequest` (57014), even at its connection limit, and has PostgreSQL's statement, idle-in-transaction, transaction, idle-session and startup timeouts; a cap on the memory all statements and transactions hold fails one past it with 53200. An error carries PostgreSQL's SQLSTATE, and its DETAIL, HINT and CONTEXT where it has them, as the ErrorResponse's own fields; a runtime error takes its SQLSTATE from the plan API, never from its message.
- **Background vacuum:** on by default in the server, with the MariaDB plugin's defaults except a fragmentation threshold of 0.7 rather than 0.5; its commit stalls writers for as long as it takes to remap the file's live keys (#337). Embedded hosts call `Database::vacuum` themselves (`docs/session_design.md`, *Background vacuum*).
- **Counters:** `select * from pg_stat_bytecask` reads the engine's operational counters over the wire, buffer pool included, as `name, value` rows, and `Database::stats` reads them in process. - **HammerDB gate:** TPROC-C over the wire, driven by HammerDB (`hammerdb/run-gate.sh`; its defaults are 48 warehouses at 1, 16 and 48 virtual users), recording the engine's counters at the end of each cell. - **HammerDB gate:** TPROC-C over the wire, driven by HammerDB 6.0 with `hammerdb/bcdboltp.tcl`, its PostgreSQL stored-procedure driver's logic calling the procedures of `hammerdb/tprocc_procs.sql` (`hammerdb/run-gate.sh`; its defaults are 48 warehouses at 1, 16 and 48 virtual users, each in `AT_EVERY_COMMIT` and `AT_INTERVAL`). - a `NUMERIC` column without a precision compared, in `ORDER BY`, `GROUP BY`, `DISTINCT` or a set operation but `UNION ALL`, in arithmetic, an aggregate but `COUNT`, cast to other than text or `name`, or as a key, unique, index or foreign-key column; `NUMERIC` without a precision as a cast target (but from jsonb), a domain or procedure argument (0A000);
- a prepared statement's fixed parameter type converted after a DDL changed its column: an integer `$n` against a column now floating-point or `DECIMAL`, any `$n` assigned to a column now a string (prepare it again);
- a comparison of columns of two tables of different types (#823), of a `DECIMAL` with another scale or number, of a `CHAR(n)` with a `VARCHAR`, of a `DATE` with a timestamp, of a `TIMESTAMP` with a `TIMESTAMPTZ`; `SUM`, `AVG`, `MIN` and `MAX` of a `REAL` column, an aggregate of `DISTINCT` values of an expression (0A000).

The functional suite (`tests/functional/`) marks what a case needs but the layer lacks, so its report shows the distance to PostgreSQL; the list above is the same gap seen from the dialect.

## Run it

```sh
xmake f --sql_layer=y
xmake build sql_layer_server
build/linux/x86_64/release/sql_layer_server --dir /tmp/db --listen 127.0.0.1:5432
psql "host=127.0.0.1 user=me dbname=db"      # the database is named after the directory
```

Flags: `--database`, `--max-connections`, `--workers`, `--thread-affinity on|off`, `--sync AT_EVERY_COMMIT|AT_INTERVAL|AT_FILE_ROTATION`, `--sync-interval-ms`, `--io-backend pread|mmap|buffer_pool`, `--buffer-pool-size`, `--buffer-pool-direct-io`, `--statement-memory-bytes`, `--max-memory-bytes`, `--statement-timeout-ms`, `--idle-in-transaction-timeout-ms`, `--transaction-timeout-ms`, `--idle-session-timeout-ms`, `--startup-timeout-ms`, `--vacuum on|off`, `--vacuum-fragmentation-threshold`, `--vacuum-busy-interval-ms`, `--vacuum-idle-interval-ms`. SIGINT or SIGTERM stops it cleanly.

The layer is part of the build only with `--sql_layer=y`, so building the engine fetches neither libpg_query (PostgreSQL licence) nor TinyCC (LGPL-2.1).

## Tests

| What | How |
|---|---|
| C++ unit tests: parser, binder, planner, codegen, golden plans, plan API, transactions, TPROC-C smoke | `xmake build sql_layer_tests && xmake run sql_layer_tests` |
| jsonb fuzz targets, the decoder's and the parser's (libFuzzer; their properties also run in `sql_layer_tests`) | `xmake f --sanitizer=fuzzer,address -m debug --sql_layer=y`, then `xmake build fuzz_sql_jsonb_decode` (or `fuzz_sql_jsonb_parse`) |
| Proof machine: random statements against PostgreSQL 17 | `BYTECASK_SQL_ORACLE=... pytest tests/proof` (needs `bytecask_sql`) |
| Wire protocol | `BYTECASK_SQL_SERVER=... pytest tests/server` |
| Functional suite: fixed cases over the wire, and a conformance report | `BYTECASK_SQL_SERVER=... pytest tests/functional`, then `--conformance --results=results.json` and `tests/functional/report.py` |
| TPROC-C in process: five transactions, consistency conditions 1–9 | `sql_layer_tprocc` |
| Isolation of concurrent transactions: point (Elle) and range histories, guarded, unguarded, blind and serializable (a third read-only too) | `scripts/sql_isolation_check.py` over `sql_layer_tprocc elle`; nightly in CI |
| SERIALIZABLE's mutations: each must fail the test its `Guarded-by:` names | `scripts/serializable_mutation_check.sh`; nightly in CI, and each patch checked to apply on every pull request |
| HammerDB gate | `hammerdb/run-gate.sh`; `--smoke` nightly in CI |

CI is `.github/workflows/sql-layer.yml`, with the sanitizers (ASan, TSan, UBSan) on the C++ tests; the isolation check is `.github/workflows/sql-layer-isolation-nightly.yml`.
